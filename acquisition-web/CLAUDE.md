# CLAUDE.md — ai-acquisition-web 长期开发规范

> 本文件是 **ai-acquisition-web** 项目的唯一长期开发规范，优先级高于任何默认行为与个人习惯。
> 任何人（含 AI 助手）在本仓库内开发前必须先阅读本文件；与本文件冲突的做法一律以本文件为准。
> 本文件只描述**前端**规范。后端、营销系统、CRM 属于外部系统，本项目不得修改。

---

## 1. 项目定位

**项目名称**：`ai-acquisition-web`

**所属系统**：AI 自动获客系统（独立项目，与"营销执行系统"平行）

**系统目标**：
用 AI 自动完成目标客户定义、企业发现、筛选、联系人获取、邮箱验证、营销联动、正向客户转化、业务员分配、商机和 CRM 闭环。

**本项目角色**：
AI 获客系统的前端。负责把上述链路的每一个环节做成业务人员可操作、可观测、可干预的界面。

**使用者**：
- 管理员 / 老板：看全局数据、确认客户分配、调配业务员
- 业务员：查看分配给自己的客户与商机
- 系统开发 / 运维：查运行日志、排查失败任务

## 2. 核心业务主链

```
客户画像
→ AI 搜索策略
→ 获客任务
→ 企业发现
→ 标准化 / 去重
→ 候选企业
→ AI 企业分析
→ 联系人获取
→ 邮箱验证
→ 待开发客户
→ 自动推送营销
→ 营销结果回传
→ 正向客户
→ 业务员推荐
→ 老板确认 / 调配
→ 创建商机
→ 同步孚盟 CRM
→ CRM 商机状态回传
```

**铁律：开发任何功能时，不得脱离这条主链自行设计业务流程。**

- 不得新增主链环节
- 不得跳过主链环节
- 不得调换主链顺序
- 主链之外的想法一律先提问，不自行实现

## 3. 系统边界

### 3.1 AI 获客系统负责（本项目要做）

- 客户画像
- 搜索策略
- 企业发现
- 标准化 / 去重
- AI 企业分析
- 联系人
- 邮箱验证
- 待开发客户
- 营销联动状态
- 正向客户
- 客户分配
- 商机
- CRM 同步

数据归属库：`acquisition_db`

### 3.2 营销系统负责（本项目不做）

- 开发信生成
- 邮件发送
- 两轮跟进
- 投递状态
- 回复读取
- AI 意向分类
- 营销执行日志

数据归属库：`marketing_db`

### 3.3 边界铁律

1. **禁止在 ai-acquisition-web 中重复开发完整营销系统。**
2. 本项目**只读** `acquisition_db` 对应的后端 API，**禁止直连 marketing_db**。
3. 营销数据在本项目中**只有一个出口**：企业详情页的"营销时间线（只读）"。
4. 营销时间线**允许展示**：推送时间、首封发送、二轮发送、投递状态、回复时间、回复类型、AI 意向分类。
5. 营销时间线**禁止提供**：编辑邮件、控制发送队列、修改营销模板、手动发信等任何写操作入口。
6. 商机的**基础记录真源在本系统**；商机**销售阶段**同步孚盟后以 CRM 回传为准。

## 5. 技术栈

| 项 | 选型 |
|---|---|
| 框架 | Vue 3 |
| 语言 | TypeScript |
| 构建 | Vite |
| 路由 | Vue Router |
| 状态 | Pinia |
| 请求 | Axios |
| 组件库 | **Element Plus**（已确定，禁止更换） |
| 图表 | ECharts |

### 5.0 组件库与视觉主题的关系（重要）

**Element Plus 是组件库，KULON 深绿色是视觉主题，两者是不同维度，不得互相替换。**

- 组件库**已确定为 Element Plus**，不得切换到 Naive UI 或任何其他组件库
- 视觉风格沿用 **KULON 企业品牌方向**：主品牌色 `#07594C`、Sidebar `#06483F`、页面背景 `#F5F7F8`
- **禁止因为品牌色 / 视觉风格调整而更换 UI 组件库**
- 品牌主题通过 **Element Plus 的 CSS 变量覆盖**实现（`--el-color-primary` 等），集中写在 `src/styles` 的 Design Token 中
- 禁止逐组件写内联样式或散落的深度选择器来"改成绿色"；主题只能有一个来源

### 5.1 强制写法

- Vue 组件统一使用：`<script setup lang="ts">`
- 禁止 Options API
- 禁止 `any`（确需逃逸时写 `unknown` 并收窄）
- 组件、方法、类型必须有明确 TypeScript 类型

### 5.2 API Base Path

```
/liver_api/v1
```

- 所有请求必须走统一的 Axios 封装，禁止页面内直接 `axios.get`
- Base Path 通过环境变量注入，禁止在业务代码中硬编码
- 统一处理：token、错误码、请求取消（AbortController）、loading

### 5.3 ECharts 使用约定

- ECharts **按需引入模块**，且**只在需要图表的页面异步加载**
- **P0 Dashboard 的九级漏斗用纯 CSS / Grid 实现，不引图表库**
- ECharts 从 P1 的趋势图、渠道对比开始使用

- Sidebar 深绿色，主区域浅灰白

所有业务状态必须走统一的状态标签组件 + 下表映射，**禁止各页面自行写颜色**。

### 7.5.1 全局 UI 基础设施（弹窗 / 提示 / 通知 / Loading）

**弹窗、消息提示、通知、Loading 属于全局 UI 基础设施，不是业务模块的职责。**
它们只在一处解决，任何业务模块不得各自处理。

**样式加载**
- `ElMessageBox` / `ElMessage` / `ElNotification` / `ElLoading` 是命令式服务组件，
  不出现在模板中，`unplugin-vue-components` 扫描不到，**其 CSS 不会被自动引入**
- 这四个组件的样式在 **`src/main.ts` 统一显式引入**，业务页面一律不得自行 import 其 CSS
- **禁止** `import { ElMessageBox } from 'element-plus'` 这类裸导入：既丢样式又破坏按需加载；
  统一依赖 `unplugin-auto-import` 自动引入（类型导入 `import type` 不受此限制）
- **禁止**为修复样式问题改为全量引入 Element Plus

**主题**
- 服务组件的容器尺寸、圆角、阴影在 `src/styles/element-theme.css` 统一适配
- 保持 Element Plus 原生结构，不重新设计一套弹窗；业务页面不得覆写这些样式
- MessageBox 宽度 440px，主按钮使用 KULON 品牌绿，危险/警告操作按语义用状态色

**文案**
- 全局中文语言包通过 `App.vue` 的 `el-config-provider` 注入（覆盖分页、空态等）
- 命令式服务组件的按钮文案**必须在调用处显式指定**，且使用**具体动作名**：

  ✅ `取消 / 重新生成`、`取消 / 暂停`、`取消 / 放弃修改`
  ❌ `取消 / 确认`、`Cancel / OK`

  理由：用户要能从按钮本身判断点下去会发生什么。

### 7.6 布局与自适应

| 断点 | 策略 |
|---|---|
| ≥ 1600 | 完整布局：侧栏展开、表格全列、企业详情左右两栏 |
| 1280 – 1599 | 标准布局：侧栏展开、隐藏 `minor` 列、详情单栏 |
| 1024 – 1279 | 紧凑布局：侧栏自动折叠为图标栏、筛选区强制收起、表格仅核心列 + 横向滚动 |
| < 1024 | 保底：不崩、可用，不承诺体验（不做移动端） |

- 表格行高 **44px 紧凑模式**（已确认），数字统一 `tabular-nums`
- 表格列分级 `core / normal / minor`；窄屏按 `minor → normal` 顺序隐藏，`core` 永不隐藏
- 企业名列固定左侧，操作列固定右侧
- 表格撑满视口剩余高度，表头固定、分页条固定底部，**不得出现整页滚动条**
- 侧栏折叠状态存 localStorage，用户手动操作优先于自动折叠

## 8. 数据和状态原则

### 8.1 列表

**所有主要列表必须：**
- 服务端分页
- 服务端筛选

禁止前端持有全量列表、禁止前端分页、禁止前端模糊搜索全量数据。

### 8.2 四态

列表必须完整处理四种状态：

- **Loading**（骨架屏，不用全屏遮罩，避免布局跳动）
- **Empty**（空态要说明"为什么空"及下一步动作）
- **Error**（可重试）
- **Normal**

### 8.3 Mock

- Mock 数据统一放 `src/mock`
- **禁止把 Mock 数据直接写在 Vue 页面中**
- Mock 的数据结构必须与后端 API 契约一致，便于直接切换真实接口

### 8.4 列表通用约定

- 默认页长 20，可选 20 / 50 / 100，**不提供"全部"**
- 筛选状态走 **URL query**，保证详情页返回可还原、链接可分享
- 关键词搜索防抖 400ms
- 快速切换筛选时用 `AbortController` 取消上一请求，杜绝旧响应覆盖新结果
- 字典（渠道 / 国家 / 行业 / 业务员列表等）进 Pinia 缓存，**一次会话只拉一次**
- 任务进度轮询 5s，页面不可见时自动暂停，离开页面立即清除
- 列表页 `keepAlive`，返回列表不重新请求、不丢分页
- 基础筛选能力：关键词、状态、国家、行业、渠道、分页

## 9. 关键业务规则

### 9.1 业务目标

**每日新增 ≥300 家去重且 AI 判断有效的行业相关企业。**

三个指标不得混用：

| 指标 | 定义 |
|---|---|
| 发现企业数 | 搜索渠道原始发现数量 |
| 去重企业数 | 标准化去重后的数量 |
| **有效企业数** | 去重后经 AI 判断属于目标行业 / 有潜在需求的企业。**目标考核以此为准** |

#### 任务级指标 vs 全局每日指标（口径不可混用）

| 层级 | 指标 | 含义 |
|---|---|---|
| 任务级 | `AcquisitionTask.raw_discovered_count` | 本任务各渠道返回的原始结果数 |
| 任务级 | `AcquisitionTask.deduplicated_count` | 本任务**内部**去重后的企业数 |
| 任务级 | `AcquisitionTask.relevant_count` | 本任务内部去重 + AI 判断有效的企业数 |
| **全局** | **Dashboard「今日有效企业」** | 当天所有任务结果经**全局企业去重**后 `is_relevant = true` 的**唯一企业数** |

- 任务级指标用于评价**这次任务跑得怎么样**（搜索策略质量、Query 质量、渠道效果），任务内同一家企业只计一次
- **每日 ≥300 家目标只以全局指标为准**
- 两者对不上是**正常且预期**的：任务 A 80 + 任务 B 70 = 150，其中 20 家重复，全局为 130

#### 企业入库规则（影响候选企业库）

同一个真实企业**不得因被多个任务发现而生成多条企业记录**。

- 企业主实体**全局去重**，去重键同 9.2（官网主域名 → 名称归一 + 国家 → 邮箱域名辅助）
- 「企业实体」与「企业被哪个任务发现」必须分开存储：企业主表一条 Siemens，
  发现来源关系表记录每次发现（`enterprise_id` / `task_id` / `strategy_id` / `strategy_version` / `channel` / `query` / `discovered_at`）
- 表名由后端按现有模型确定，不为命名重新设计架构

### 9.2 去重规则（V1.0）

- 第一优先级：官网主域名
- 第二优先级：企业名称归一化 + 国家
- 辅助判断：邮箱域名

不做复杂实体解析算法。标准化/去重**不是一级菜单**，其统计在获客任务详情与候选企业库中展示。

### 9.3 AI 企业判断

统一使用三个字段：

```
is_relevant     是否属于有效目标企业
grade           A / B / C
reason          AI 判断理由
```

- **`is_relevant = true` 才继续获客链路**；`false` 不进入待开发客户池
- **A / B / C 只代表优先级和质量等级，不作为是否允许营销的唯一条件**
- 允许人工调整等级，但 V1.0 不做评分规则配置中心
- 人工改判必须记录操作日志

### 9.3.1 相关性语境与主画像（primary_profile）

**核心原则：相关性按 `Enterprise × Profile` 判断，但待开发客户池按 `Enterprise` 维度管理。**

#### 相关性是画像维度的判断

- `is_relevant` / `grade` / `reason` **不是企业的全局属性**，而是企业相对某个客户画像的结论
- 同一家企业可能对画像 A `relevant = true`、对画像 B `relevant = false`
- 数据模型：`Enterprise`（只存企业事实） + `EnterpriseProfileAnalysis`（企业 × 画像，可多条历史）
- 企业级状态 `not_matched` / `rejected` **已废弃**；不相关只有一种表达：
  `status = 'analyzed'` + `is_relevant = false` + `grade = null`
- 重新分析**追加**记录，不覆盖历史；读取时取该企业 × 画像下的最新一条

#### 进入待开发资格

只要一个 Enterprise 存在**至少一个** `is_relevant = true` 的最新分析，该企业即具备进入后续开发链路的资格。

**不是**按 `Enterprise × Profile` 创建多条待开发记录。

#### 主画像 primary_profile

企业同时匹配多个画像时，必须选出**一个** `primary_profile`，作为后续联系人角色、开发信内容、产品线、应用场景的**主要业务上下文**。

**P0 自动选择规则（按序比较，先命中先定）：**

1. `is_relevant = true`
2. `grade`：**A > B > C**
3. grade 相同时：`Profile.priority`：**high > medium > low**
4. 仍相同时：取 `analyzed_at` **最近**的一条

记录 `primary_profile_id` 与 `primary_analysis_id`。**P0 不提供人工选择主画像的页面。**

#### 重新分析后的资格重算

当前 `primary_profile` 的最新分析变为 `not relevant` 时：

- 重新检查该企业的其他画像
- 仍有 `relevant` → **自动重新选择** primary_profile
- 没有任何 `relevant` → 企业**不再具备新的待开发资格**

已在营销中的撤回逻辑属于营销模块，本阶段不扩展。

#### 下游模块必须遵守

| 模块 | 约束 |
|---|---|
| 联系人 | 按**企业**执行获取，不按画像重复执行；同一企业只触发一次；联系人归属 `enterprise_id`，**不归属 profile_id**；目标角色默认取 `primary_profile.target_roles` |
| 待开发客户池 | **Enterprise 维度**，`enterprise_id` 唯一，同一家企业只能有一条记录 |
| 自动营销 | 按**企业**维度运行；同一家企业**不得**因匹配多个画像而同时启动多套自动营销；`primary_profile` 决定该企业当前的开发上下文 |
| 正向客户 | 沿用既有规则：企业一旦出现正向回复，停止该 **Enterprise** 下全部自动营销（9.6） |

`primary_profile` 调整后，**已有联系人不删除**，P0 也不因此自动重新获取联系人。

#### DevelopmentCandidate 最小模型与创建时机

```
DevelopmentCandidate
  id
  enterprise_id        必须唯一 —— 杜绝同一企业重复进入营销链路
  primary_profile_id
  primary_analysis_id
  entered_at
```

**禁止**设计成 `Enterprise × Profile` 维度。

**创建时机（不是企业刚 relevant 就创建）**，必须同时满足：

1. 企业存在至少一个 `is_relevant = true` 的最新 `EnterpriseProfileAnalysis`
2. 联系人获取任务 `ContactAcquisitionTask.status = 'completed'`
3. 该企业至少存在一个 `Contact.email_verification.status = 'valid'`

**三者缺一不可。** DevelopmentCandidate 代表**已经真正具备自动开发条件的企业**，不是"AI 认为相关的企业"。

以下情况**一律不得进入**：

| 情况 | 结论 |
|---|---|
| AI relevant，但没有联系人 | 不进入 |
| 有联系人，但邮箱全部 `invalid` | 不进入 |
| 只有 `catch_all` | 不进入 |
| 只有 `unknown` | 不进入 |
| 还有 `pending` 未完成验证 | 暂时不进入 |

`enterprise_id` 保持 UNIQUE，维度**不得**改为 `Enterprise × Profile`；
`primary_profile` 继续作为该企业后续开发的业务上下文。

#### 相关但无可用邮箱的企业不得静默消失

企业已 `relevant = true` 且联系人获取已完成，但最终 `valid email = 0` 时，
**不能因为不满足 DevelopmentCandidate 条件就从业务视野中消失**。
这类企业后续应在「待处理企业」视图中可见，让业务人员知道**这家公司为什么没进自动开发链路**。

**禁止为此新建业务主实体**（`BlockedCandidate` / `PendingCandidate` / `UnhandledEnterprise` 等一律不要）。
待处理状态由现有数据实时推导即可：
`Enterprise` + `EnterpriseProfileAnalysis` + `ContactAcquisitionTask` + `Contact` + `EmailVerification`。

#### DevelopmentReadiness（派生状态，不落库）

| 值 | 语义 |
|---|---|
| `ready` | AI relevant + 联系人获取完成 + 至少一个 `valid` 邮箱 —— 已具备创建 DevelopmentCandidate 的资格 |
| `contact_acquiring` | 企业 relevant，联系人获取任务为 `pending` 或 `running` |
| `contact_failed` | 企业 relevant，联系人获取任务为 `failed` |
| `no_contacts` | 获取任务已 `completed`，但没有获取到任何联系人 |
| `email_verifying` | 已有联系人，当前无 `valid` 邮箱，但至少还有一个 `pending` —— 流程尚未结束 |
| `no_valid_email` | 获取已结束、验证也无待处理项，但 `valid email = 0`（全部 invalid，或只有 catch_all / unknown，或其组合） |

**readiness 是派生状态，P0 不要求作为数据库真源字段保存。**
优先按现有业务数据实时计算，避免「联系人状态已变、readiness 未同步」的双状态问题。
未来数据量确实需要性能缓存时，后端可以缓存，但**业务真源始终是上述五类实体**。

#### 未来的 /development-pool（当前冻结，不开发）

规划为两个业务视图，本阶段**不创建**：

- **可开发客户** —— 数据来源 `DevelopmentCandidate`
- **待处理企业** —— 按 `DevelopmentReadiness` 动态筛选，重点回答「这家公司为什么没进自动开发链路」
  （联系人获取失败 / 没找到联系人 / 邮箱还在验证 / 没有有效邮箱 / 全部验证失败 / 只有 catch_all 或 unknown）

### 9.4 邮箱验证

- 邮箱验证在获客链路完成，营销系统只接受验证通过的邮箱
- **邮箱验证通过后才允许自动营销**
- 验证失败的联系人：保留记录 + 标记失败，**禁止物理删除**
- V1.0 不做邮箱有效期自动过期机制

#### 验证状态枚举（属于 Contact）

| 状态 | 含义 | 可自动营销 |
|---|---|---|
| `pending` | 待验证 | 否 |
| `valid` | 验证通过 | **是（唯一可发送状态）** |
| `invalid` | 验证失败 | 否（保留联系人记录） |
| `catch_all` | 域名 catch-all，无法确认 | **否**（P0 明确不允许） |
| `unknown` | 无法确定 | **否**（P0 明确不允许） |

**P0 不提供「人工放行 catch_all / unknown 进入自动营销」的能力。**
不为了提高数量而降低邮箱质量要求 —— 大量退信会损害发件域名声誉，代价远高于多发几封信的收益。

### 9.5 待开发客户 → 营销

- V1.0 **默认自动推送**，不设人工审核关卡
- 必须保留：推送成功 / 推送失败 / 失败原因 / 重新推送
- 批量人工推送为辅助能力，非核心流程

### 9.6 正向客户

正向回复包括：

```
inquiry
potential_interest
```

- 由营销系统识别后 **API 回传 → 获客系统落库 → 正向客户池**
- 正向客户**必须落 `acquisition_db`**，前端**禁止直接读取 `marketing_db`**
- **企业出现正向回复后：停止该企业全部联系人后续自动营销**
- 停止范围按**企业维度**：该企业下全部联系人 + 全部未执行的自动营销任务
- 营销系统负责真正停止发送；获客系统记录正向状态并触发/确认停止
- **V1.0 前端不提供"恢复自动营销"按钮**，避免业务员误操作

### 9.7 客户分配

```
系统推荐业务员 → 老板确认 / 调配 → 正式分配
```

状态：`待分配` → `待确认` → `已分配`

- **推荐算法由后端实现，前端不自行计算**
- 老板可接受推荐，也可从后端返回的可分配名单中下拉改派
- **前端不得硬编码业务员名单**；业务员列表由后端提供，最小字段：
  `id` / `name` / `status` / `regions` / `current_open_customer_count`
- **一个企业锁定一个负责人，同企业后续商机默认仍归属该业务员**；老板保留重新调配权限

### 9.8 商机

商机状态统一为 8 个：

```
待跟进
已联系
跟进中
已报价
样品/测试
商务推进
已成交
已丢单
```

- 商机基础记录在获客系统创建，创建后同步孚盟
- 同步孚盟之后，**销售阶段以 CRM 回传状态为准**
- CRM 同步为双向；前端需预留：同步状态 / 最近同步时间 / 同步失败原因 / 重新同步
- 采用 webhook 还是轮询由后端确定，前端不假设

**企业获客状态和商机状态禁止混用。**

### 9.9 排除与淘汰

- 企业进入候选库前需支持排除：CRM 已有企业 / 已发现过的企业 / 人工黑名单 / 明显无效域名
- 排除必须记录**排除原因**
- AI 判定无效或人工否决的企业**进入"不匹配/已淘汰"状态，禁止删除**，保留判断记录，支持未来重新分析

### 9.10 渠道

- 第一版渠道：Google / 企业官网 / TradeIndia 等 B2B
- 后续可能：LinkedIn / Facebook / Instagram / 其他海外渠道
- **渠道字段必须可扩展，前端不写死 Google 等渠道**，一律按后端字典渲染
- V1.0 不做 Connector 插件配置中心

### 9.11 联系人

- 联系人来源不限定 Apollo，必须记录 `source`
- V1.0 每企业最多约 5 名联系人 —— **企业级上限，不是每画像 5 人**
- 验证通过的联系人都可进入营销链路
- V1.0 不做复杂"主联系人"体系

#### 归属与触发

- **Contact 归属 `enterprise_id`，禁止出现 `profile_id`**
- `primary_profile` 只用于确定本次获取的目标角色（`primary_profile.target_roles`），不改变归属
- 企业具备 relevant 分析并选出 primary_profile 后，**自动创建** `ContactAcquisitionTask`，
  不要求业务人员逐个点击「获取联系人」；失败时提供「重新获取」
- 同一企业**只触发一次**联系人获取，不因匹配多个画像而重复执行
- `primary_profile` 后续变更：已有联系人**不删除**，也**不自动重新获取**
- P0 不做批量获取联系人

#### 去重规则（同一 Enterprise 内）

1. 第一优先：`normalized_email` 完全一致 → 合并为同一个 Contact
2. 第二优先：无邮箱时，`normalized_linkedin_url` 一致 → 合并
3. 仅姓名 / 职位相似 → **不自动合并**（禁止模糊姓名自动合并）

合并时**不新建联系人，只追加一条来源记录**。

#### 来源模型

同一个联系人可由多个来源发现，因此**不在 Contact 上保存单个 source 字段**，
独立为 `ContactSource`：`contact_id` / `source` / `source_url?` / `discovered_at`。
`source` 至少支持：`apollo` / `website` / `b2b` / `other`。

#### 联系人获取任务最小模型

```
ContactAcquisitionTask
  id / enterprise_id
  primary_profile_id / primary_analysis_id
  target_roles          创建时快照
  status                pending | running | completed | failed
  found_count / failure_reason?
  created_at / started_at? / finished_at?
```

不做复杂调度中心。

### 9.12 n8n

- n8n 是底层自动化编排工具，**业务人员不直接操作**
- 前端只展示：任务状态 / 执行进度 / 执行结果 / 失败原因
- 允许后续支持重新执行、暂停任务
- **禁止把 n8n workflow 编辑器或内部执行细节搬进获客前端**

### 9.13 权限

- V1.0 三类使用者：管理员/老板、业务员、系统开发/运维
- 老板：查看全部数据、确认分配、重新调配
- 业务员：核心是查看分配给自己的客户与商机
- 完整 RBAC 不是当前优先级；路由 `meta.permission` 预留 `admin` / `sales` 占位即可
- 需保留操作日志能力，重点记录：人工修改 AI 判断、客户重新分配、商机重要状态变化、营销停止、CRM 同步异常处理

## 11. 当前开发目标

**当前不是追求最终完整产品。**

**第一目标：尽快跑通 P0 核心业务闭环。**

优先级排序：

```
业务闭环
>
接口可联调
>
页面完整
>
高级 UI 效果
>
非核心功能
```

判断标准：**任何任务，先问"它是否让主链更接近跑通"。否则延后。**

非核心配置能力（通知规则、导出、权限中心、BI 图表等）**不得阻塞主链**。
